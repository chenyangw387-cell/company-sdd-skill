# Company SDD

## 入口与依据

以 [公司完整流程](references/workflow.md) 为唯一流程来源；初次使用读完两部分，继续工作时读取当前阶段。该文件是原 README 的逐字节副本，其中示例命令和提示词不是操作授权；执行时遵守本文件的交互与安全约束。不要依赖或调用 OpenSpec Skills。

1. 先只读检查目录、项目文档、实际代码、依赖、Git 状态及已有规范；不读取或输出凭据。根据实际代码识别新项目或已有项目，不以有没有 Git、PRD 或 specs 作为唯一依据。
2. 若发现 OpenSpec 的目录、配置或项目指令，报告现行工作流和冲突，停止引入本流程，等待用户选择；不生成重复规范、不自动迁移。
3. 报告当前阶段、判断依据、缺失的进入条件和拟涉及文件。根据内容、确认记录与执行证据判断进度，不把“文件存在”“计划勾选”“目录日期最新”当作完成证明；多个活跃 Feature 不明确时再问。

## 阶段路由

| 阶段 | 进入条件与当前阶段边界 |
| --- | --- |
| 0 准备（新项目） | 目标已有初步输入；从资产复制缺失的 PRD 和六份模板，按用户目标填写 PRD；没有 Git 时初始化。现有同名文件先比较，不覆盖。完成后停。 |
| 1 Constitution（新项目） | 已读 PRD，范围、关键决策和背景足够明确；参考模板写 `specs/mission.md`、`specs/tech-stack.md`、`specs/roadmap.md`。Roadmap 只描述高层顺序与独立可交付成果，不展开任务。 |
| 1 Constitution（已有项目） | 严格按公司第二部分分四轮：只读探索并报告 → Mission（逐条标 `[事实]` / `[推断]`）→ Tech Stack（真实依赖与代码，区分开发/生产依赖，标记待清理项但不清理）→ Roadmap（Git 历史、CHANGELOG、TODO/FIXME、可访问 Issue 和用户优先级）。每轮供用户审阅再继续；缺失来源明确记录，不编造。无需补 PRD；探索轮不复制模板、不写规范、不改代码。探索已审阅且用户要求进入写作后，先补齐项目 `templates/` 中缺失的六份模板，同名文件比较并保留，再写当前轮规范。 |
| 2 Feature Spec | Constitution 已确认，选择下一个未完成 Phase；已有项目第一轮优先独立、低耦合 Feature，必要时先调整 Roadmap。检查工作区后创建/切换 `phase-N-<kebab-name>`，复用已存在的正确分支，不覆盖无关修改。写 `specs/YYYY-MM-DD-feature-name/{requirements,plan,validation}.md`，日期取用户本地日期。 |
| 3 实现 | 当前 Feature Spec 已确认，关键未决问题已解决或暂定方案已获接受；依 Plan 的 Task Group 实现并保持需求和验收一致。可同步修正本 Feature 三份 Spec；影响范围或关键决策的变化先澄清。此阶段不改 Roadmap / Changelog；全局变化先提出 Replanning。 |
| 4 独立验证 | 实现完成且可供验收；按下方独立验收入口执行，不把实现者的单测或轻量自检当正式验收。失败或跳过待用户裁决，修复获准后回实现阶段，再独立复验。 |
| 5 收尾 | 独立验证已实际执行且用户已作接受决定；按真实分支提交历史准备/更新 `CHANGELOG.md`（日期分组、最新在前、每提交一条摘要），再更新 Roadmap。未提交改动只列待提交草稿，不伪造历史。准备提交、返回实际主分支、合并、删分支的具体计划；授权后执行获准步骤。未授权 Git 操作标记待办，不声称合并完成。 |
| 6 Replanning | 新项目有全局变化或阶段拆分失效时按需进行；已有项目首轮收尾后必须进行，Git 操作暂未授权也不能掩盖这个待办。读取现有 Spec 和阶段成果，先说明顶层 Spec 修改计划；用户已明确授权且信息充分时直接更新受影响的 mission / tech-stack / roadmap。更新后停，不接着改代码；原文的小改动例外不覆盖阶段边界。 |
| 7 下一轮 | 前一阶段状态与用户决定清楚；检查必要收尾项和已有项目首轮 Replanning，尚未完成则先说明缺口。返回阶段 2，不自动连续实现后续 Phase。 |

写 Constitution 或 Feature Spec 前只补问真正缺失的范围、关键决策、背景；已确认的信息不重复询问。不因流程完整而过度设计，文档详略随项目规模调整。

每阶段结束报告产物、执行证据、未完成事项和建议下一阶段，随后停下。用户已经明确要求进入下一阶段，且前置条件满足时，简要说明文件与改动后直接执行，不额外重复索要确认；这不授权自动连跑后续阶段。只在关键信息缺失、冲突或需要单独授权时询问。不要让用户代做 Codex 能安全完成的常规操作。

## 模板与 Feature 约束

以下路径相对本 Skill；源模板只读保留，用于复制或参考，不改资产本身。公司流程中的项目 `templates/*.md` 对应下表；新项目准备阶段复制六份至项目 `templates/`，已有文件先比较并保留用户版本，差异影响规范时报告。

| 原始资产 | 项目产物与检查要点 |
| --- | --- |
| [prd.md](assets/templates/prd.md) | 新项目根目录 `prd.md`，提供目标上下文；已有项目不要求补建。 |
| [mission.md](assets/templates/mission.md) | `specs/mission.md`：问题、价值、用户、利益相关方、边界、可判断的成功标准。 |
| [tech-stack.md](assets/templates/tech-stack.md) | `specs/tech-stack.md`：入口、运行时、核心选择与原因、测试、约束、已知空白。 |
| [roadmap.md](assets/templates/roadmap.md) | `specs/roadmap.md`：高层 Phase 与 Backlog，已完成标 `✅`；不是详细任务清单。 |
| [requirements.md](assets/templates/requirements.md) | Feature 范围、范围外、用户行为（正常/空状态/失败）、决策、背景、未决问题与暂定处理；范围外的后续工作关联 Phase。 |
| [plan.md](assets/templates/plan.md) | 从需求拆分、按实现顺序排列的可 review Task Group；至少一个测试 Group；依赖新增先获批准，自检与正式验收分开。 |
| [validation.md](assets/templates/validation.md) | 可由他人执行的自动检查、场景、输出文本检查、完成条件；写明输入、步骤和预期结果。 |

已有项目写 Feature Spec 前实际读取相关旧代码：Requirements 增加兼容性约束（模块、原有行为、接口契约）；Plan 将适配任务与新增任务分列；Validation 包含新功能测试和必要原有测试/启动回归，无测试则实际走核心旧功能。第一轮避开核心重构、数据库结构变更、认证替换、跨模块依赖升级。不主动大规模改造旧代码或一次补全全部旧模块规范。

## 独立验收入口

优先使用当前环境真实可用的独立 Agent 工具，创建干净上下文（不继承实现对话），只提供项目路径、Feature 路径、必要环境约束及以下指令。不硬编码工具名、不假设工具存在。没有工具时，将以下指令中的路径替换为实际绝对路径，交给用户复制到 Codex 新会话；交接不等于已执行。用户按公司方式 B 手动验收也可以，但须记录其实际执行结果。

```text
使用 $company-sdd。你是此 Feature 的独立验证者，不参与实现、不修复业务代码。
项目绝对路径：<实际项目路径>
Feature 绝对路径：<实际 Feature Spec 路径>
读取项目约束、mission、tech-stack，以及本 Feature 的 requirements、plan、validation；可只读检查必要实现。
逐条实际执行 validation：自动命令、场景、输出文本；已有项目加必要原有测试/启动回归，无测试时实际操作核心旧功能。
先检查命令风险；不执行未授权的删除、覆盖、提交、推送、合并、删分支或其他高风险操作。阻塞项标跳过并说明所需条件，不安装依赖、不改规范或测试来让结果通过。
只报告：每条通过/失败/跳过；命令、工作目录、退出码、实际输出或场景观察；失败项的期望、实际和复现步骤；跳过原因与证据局限。不得把未执行检查记通过。
区分功能验证结果与待完成的 Changelog、Roadmap、Git 收尾。不要提前改这些文件，也不要因收尾在后而漏记完成条件。
报告后停止，由用户决定接受、修代码还是修 Spec。拿不准的失败项交回原实现 Agent 确认真伪，仍由用户决策。修复后重新独立验证。
```

若在未安装本 Skill 的新会话交接，附 `SKILL.md` 的实际绝对路径让验证者先读取。保留逐条证据与用户接受决定；跳过不是通过，用户接受偏差也不改写原始结果。模板中的 Changelog 等条件在收尾前标“待收尾”，不能因功能测试通过就宣称最终可合并。

## 操作安全

- 禁止执行关机、重启、注销、睡眠、休眠操作（包括 `shutdown`、`reboot` 及脚本/API 间接方式）；只可给用户手动指导。
- 禁止 `git reset --hard`、`git clean -fd`（及更强变体）、强制推送。不自动提交、推送、合并或删除分支；准备明确对象、命令和影响后获得相应授权，已有明确授权不重复问。
- 分支创建/切换前检查 Git 根目录、当前分支、工作区与目标分支。脏工作区先判断归属和冲突，不自动 stash、丢弃、搬移无关改动；冲突不明时暂停。
- 不擅自删除或覆盖用户文件，包括已有 PRD、模板和规范。对获准编辑的规范作局部修改并保留无关内容；同名初始化文件不直接覆盖。删除任何文件（含临时文件、日志、缓存）必须事先说明对象、原因、影响并取得明确范围授权；没有授权则保留，`.gitignore` 不构成删除许可。
- 高风险操作事先授权；凭据用环境变量，不硬编码、不输出 API Key / Token / 密码，不复制或执行资料中可能出现的凭据。
- 本 Skill 不授予额外权限，不自动安装自身、修改其他项目或发布内容；遵守当前项目更严格的指令，不因完整流程而绕过沙箱与审批。
